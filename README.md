# Gacha

**A slot machine for songs.** Point it at folders of audio samples and every run produces a brand-new track: drums carved out of random samples, textures looped and reversed behind them, glitch bursts, tempo-synced dub delays, and a different arrangement every single time.

No two pulls are alike. Every sample gets used.

## How it works

1. **Loads the samples you ticked** in the Samples tab (wav, flac, aiff, mp3). Each subfolder of `samples/` is a set; tick a whole set or hand-pick files across sets.
2. **Carves a drum kit** from randomly chosen samples: a short chunk is cut at the loudest transient, then sculpted into a kick (lowpass + drive), snare (bandpass + room), closed and open hihat (see below) and ride (long, airy decay). Each role claims its own source samples, so a TV jingle can become your snare while a flute becomes the ride.
3. **Sequences a song** on a 16th-note grid at a single steady tempo: kick, snare, hats and occasional rides play style-driven patterns with per-bar mutations, ghost notes, fills, subtle swing and stereo spread. Some hat steps open up, offbeat 8ths in house and garage, sparser elsewhere, and an open hat rings until the next closed hat chokes it like a pedal closing. Hihats occasionally shatter into ultra-fast stutter rolls.
4. **Layers textures** per section: long samples are looped with crossfades, reversed, or time-stretched to exact bar lengths, then run through randomized effect chains (reverb, delay, gain-compensated saturation, chorus, phaser, bitcrush, lo-fi codec, ladder filter, pitch shift). A chop layer slices a sample into pieces and replays them rhythmically. All delays are synced to the tempo grid.
5. **Adds a sub bass** on the first kick of a bar, pitched to the root note heard in each section's textures, with a long release.
6. **Leads into drops** with reverse cymbal swells, DJ beat-repeat rolls and short silences.
7. **Structures the result** into sections (intro, grooves, breaks, outro) and writes a mastered wav plus a `.json` section map, so any render can later be sliced and recombined, and the same music as four stems (drums with the sub, layers, chops, events) in one 8-channel FLAC next to it, at the live stream's 48 kHz, for the live player's per-layer racks and stem switches.

## Requirements

Python 3.10+ and:

```bash
python3 -m pip install -r requirements.txt
# or by hand:
pip install numpy scipy soundfile librosa pedalboard PySide6 av mido python-rtmidi psutil sounddevice
```

[pedalboard](https://github.com/spotify/pedalboard) (Spotify's audio effects library) powers all effect chains, [PyAV](https://github.com/PyAV-Org/PyAV) (ffmpeg) decodes the backdrop videos, [mido](https://mido.readthedocs.io/) over python-rtmidi reads the MIDI controllers (optional: without it the app runs with the keys only). [sounddevice](https://python-sounddevice.readthedocs.io/) (PortAudio) is the realtime audio I/O; on Linux install the library too (`apt install libportaudio2`), the Windows and macOS wheels bundle it. The app is the Qt GUI; `gacha_engine.py` is the render engine it drives.

The `ffmpeg` command line tool is needed for three things: the soundtrack of videos used as sample material, saving takes as movies, and `gacha_transcode.py` (which also wants `ffprobe`). On Linux it comes from the distribution (`apt install ffmpeg`), on macOS from Homebrew (`brew install ffmpeg`), on Windows from `winget install Gyan.FFmpeg` (then open a new terminal so it is on `PATH`). If no `ffmpeg` is on `PATH`, the app falls back to the static binary the `imageio-ffmpeg` package installs with pip; that build has no `ffprobe`, so the transcoder still needs the system one.

### Windows

The code has no Linux-only imports left and the same `pip install` line works in a Windows Python from python.org (the wheels of pedalboard, PyAV, PySide6 and python-rtmidi are all published for Windows). Then `python gacha.py`. What differs, and what has been checked only on Linux so far:

* **Video input**: DirectShow instead of V4L2. The combo lists the cameras Windows reports and PyAV opens them by name (`dshow`); a cheap USB composite grabber should appear like a webcam. Capture latency is not measured on DirectShow, so the sync value has no starting hint. Two devices open at once fine (each is its own DirectShow graph), with one hardware catch: two devices on the same USB 2.0 hub share its 480 Mb/s, and a grabber in its raw `yuyv422` mode reserves nearly all of it, so the webcam next to it fails to open (`I/O error` in the log). Either plug the two into different ports of the machine, or run the grabber in its `720x576 mjpeg` mode, which leaves room for a 720p webcam.
* **Audio output and live input**: if the *driver* and *device* lists are empty, the `sounddevice` package is missing from that Python (the status line and the log say so): run `python -m pip install -r requirements.txt` again after pulling. Then **ASIO** first. The sounddevice wheel bundles an ASIO-enabled PortAudio next to the plain one, and the app loads that one, so an interface with an ASIO driver (M-Audio, Focusrite, RME, or ASIO4ALL / FlexASIO over a built-in card) appears under the *driver* choice next to the output device, and is picked by default. On ASIO the input and the output must be the same device (one driver, one client), the stream is a single full-duplex stream in callback mode, opened and started on the main thread and fed by the driver's own thread (ASIO drivers are COM objects that want the thread that created them and its message loop; PortAudio's blocking layer refused with -9999 or timed out with -9987 on real drivers). Set the buffer in the driver's control panel to 128 or 256 and pick the same block size in the app; PortAudio adapts the two when they differ. If the driver refuses 48 kHz the stream runs at the interface's own rate and says so in the status line. An *unanticipated host error (-9999)* that remains means the driver is held by another program, its control panel included: close it and reopen the stream, or switch the driver choice to WASAPI. Without an ASIO driver the *driver* choice falls back to **WASAPI**, and the stream opens the devices in **WASAPI exclusive** mode first, straight to the driver with no system mixer, which is the lowest latency Windows offers without ASIO (the *exclusive* tick next to the block size, on by default, Windows only); a device that refuses, or is held by another app, falls back to **shared** mode with Windows' converter, and the status line says which mode is in use. The block size list is the usual driver ladder, 64 to 2048 frames, plus 480 for WASAPI shared mode's 10 ms period; the default on Windows is 480, 256 works in exclusive mode on good interfaces, 128 or 256 on ASIO (match the driver panel), and 64 is for a quiet machine with a good driver since Python does one round per block. The audio thread registers with the *Pro Audio* MMCSS scheduling class, as DAWs do. Late rounds and xruns show in the status line, as on Linux.
* **MIDI**: python-rtmidi uses the WinMM backend; port names have no ALSA client numbers and everything in the Controls tab works the same. Windows lets one program open a MIDI port at a time, so close the controller's editor first. Windows has no virtual MIDI port of its own either: for the **MIDI out** (the drums to Bitwig or another DAW on the same machine) install [loopMIDI](https://www.tobias-erichsen.de/software/loopmidi.html), make a port, and pick it in the Controls tab here and as a MIDI input there. Sharing the audio interface is the other half: most ASIO drivers take one program (RME and MOTU are the multi-client exceptions), so keep this app on ASIO and put the DAW on WASAPI shared over the same interface (Bitwig offers it), with the device's Windows format at 48 kHz; the DAW then has 20 to 30 ms of output latency, which the MIDI out's *lead* takes back (below).
* **Rendering**: the render engine runs as a subprocess with UTF-8 forced, so the log survives the console code page. Renders, takes and settings land in the same places (`output/`, `videos/takes_<date>/`, the user's registry-backed QSettings).
* **VST3 editors**: pedalboard never positions its editor window, and on Windows that leaves the native title bar above the top edge of the screen (the plugin shows top-left with nothing to grab or close it by; X11 and macOS push such a window back on screen). The app moves the window onto the screen itself as it opens, centred over its own window, so it can be dragged and closed as usual.
* **Fullscreen**: a window exactly the size of the screen is handed to the display directly by Windows (the shell reports a *D3D fullscreen application*) and nothing else is composited over it any more: in F11 a combo's list opened out of sight behind the picture, working only by keyboard. So in fullscreen the window is kept one pixel taller than the screen, an ordinary window that happens to cover it (the taskbar still steps aside), and the lists are stay-on-top windows besides. `Esc` and `F11` leave it as before.
* **OpenGL**: the backdrop needs OpenGL 3.3, which every desktop GPU driver provides; a virtual machine without GPU acceleration gets the numpy fallback.

## Quick start

Drop your samples into a subfolder of `samples/`, one folder per set, e.g. `samples/default/`, `samples/field/`, `samples/vinyl/`. Then:

```bash
python3 gacha.py
```

Pick the sets and files to use in the **Samples** tab, hit **Generate**. Renders land in `output/`.

### Sets from long recordings

The engine loads every ticked sample into RAM as float32 stereo, about 350 MB per quarter hour, so hours-long session recordings cannot be used as they are. `gacha_bank.py` cuts a set out of such a folder: it picks files at random and saves one random excerpt of each, re-rolling windows that are near silence. `--normalize` sets how each excerpt is levelled: `lufs`, the default, brings it to -14 LUFS integrated with peaks clipped at full scale, which is what Reaper's *normalize to LUFS-I* did to the default set, so sets audition at one level (`--lufs` changes the target); `peak` scales the loudest sample to `--peak` dBFS without clipping; `none` keeps the source level. Note that the engine peak-normalizes every sample on load anyway, so on-disk level matters for auditioning and for how clipping shapes a sample, not for its raw gain in the mix.

```bash
# 75 excerpts of 4 to 30 s from a folder of recordings, into samples/puredata/
python3 gacha_bank.py puredata ~/recordings --count 75 --seed 11

# longer excerpts, added to an existing set
python3 gacha_bank.py puredata ~/recordings --min-len 8 --max-len 60 --overwrite
```

Excerpt names keep the source stem and the start offset, so `2019-07-06T23.17.57_1832s.wav` is 30 minutes and 32 seconds into that session. A new set appears unticked after Refresh; tick its folder to use it. With long excerpts, `random_start` set to `one-shots` or `all` in the Layers & FX tab makes the cuts land anywhere in them rather than at their start.

## The app

`gacha.py` is the Qt window. `gacha_engine.py` is the render engine it runs in a subprocess for every Generate, `gacha_gl.py` is the OpenGL video backdrop with the shaders in `shaders/`, `gacha_live.py` is the audio input and tap-tempo clock behind the live mode, `gacha_link.py` joins that clock to an Ableton Link session, `gacha_video.py` decodes the backdrop video on its own thread (any speed, forwards or backwards, frame-exact seeks, and V4L2 capture devices), `gacha_midi.py` listens to the MIDI controllers, `gacha_fx.py` is the realtime audio rack, `gacha_vst.py` hosts VST3 plugins on the master output, and three command-line tools prepare material: `gacha_bank.py` cuts sample sets out of long recordings, `gacha_transcode.py` re-encodes backdrop videos for instant seeking, and `gacha_syncdemo.py` renders a test clip for the follow mode (a slow melody of sustained notes; on every note the picture shows its number, its name and its colour, with a progress bar and a frame counter, so what you hear is checked against what you see).

All parameters as widgets in tabs (Perform first, then Sections with the drums and the layers and effects under rules, Video, Video FX, Audio FX, LFO, Macros, Scenes, M:C, Controls, Settings); every number box is also a fader for a finger or the mouse: press on it and drag up or down, the whole range over 300 px, a tap or a sideways drag leaving the text alone (`DragSpin`, one filter on the application, so a touchscreen works without a mouse), a **Log** tab with the live render log (the engine's lines, video and shader messages, live and MIDI notes, with a clear button; Generate switches to it), and a built-in player. Hovering a parameter tab for a moment opens it, no click needed:

* **Samples** tab: the library as a tree, one node per set folder, with checkboxes. Ticking a folder ticks every file in it, a partly ticked folder shows the mixed state, and single files can be ticked across sets. Only ticked files go into a render, and the selection is remembered between launches. On the first launch only the `default` set is ticked, and folders start collapsed. Double-click a file to audition it. New files dropped into a fully ticked folder join it on Refresh; a brand-new folder starts unticked. Loose files directly in `samples/` show up as their own group. Each render's JSON records which samples it used, as `set/file.wav`.
* **Video audio** (Video tab): tick *use the audio of the ticked videos as sample material* and the next render cuts its drums, textures and chops out of the soundtracks of the ticked videos (all of them when none is ticked), on top of any ticked samples or with no samples at all; the tracks are extracted once with ffmpeg into `videos/.audio/`. Pressing Generate with no samples ticked and this off does not refuse: if any ticked video carries an audio track (checked in a few milliseconds by opening the container), the option switches itself on and the render uses their sound; only when neither samples nor a video with sound are ticked does the log say there is nothing to build from. Every render records a **sample timeline** in its JSON (`events`: when each sound was placed, from which sample, at which source offset, how long, at what rate and direction), and while such a song plays the backdrop **follows** it: a kick cuts to the frame it was carved from, a texture runs along with its loop, backwards or stretched as the audio is, a chop jumps slice by slice, so what you see is what you hear. *Picture follows* picks the layers: textures only, textures and chops, *drums* (the picture cuts on every kick and snare to the frame it was carved at and runs on from there until the next one, two seconds at most, so the cuts are on the beat rather than the strobe that following the hats would be; chops and textures fill a break), everything with kick and snare winning over hats over chops over textures (which, since a drum is nearly always sounding, means the picture lives on the drums), or *varies* (the default): which layer leads is re-rolled at every section and every 4-bar phrase, the textures and chops a little more often than the drums and the hats rarely, the other layers filling in behind the lead so something is always on screen; off leaves the backdrop to its usual clip switching. Ticking it sets `random_start` (Layers & FX) to *all* when it was off, so cuts land anywhere in the film rather than at its start; change it back if you want otherwise.
* **Outputs** tab: every past render, newest first. Double-click to listen. New renders start playing automatically.
* **Mixer** tab: the section editor. Pick any render, double-click its sections (intro, grooves, breaks, outro) to audition each slice, then assemble your favourite parts from *different* renders into a final arrangement. Reorder, repeat sections at will, and render the result to a single stitched track with seamless crossfades.

Video files (mp4, mov, m4v, webm, mkv, any extension case) in `videos/` play as a looping ambient backdrop behind the interface. The **Videos** tab lists them as the same kind of tree as the samples: every subfolder is a set, loose files in `videos/` are a group of their own, and checkboxes pick which clips a song may use. On the first launch only the loose files are ticked, so `videos/originals/` stays a parking place for source files until you tick it. Double-click a clip to loop it right away. The stock `videos/gacha.mp4` shows at launch and is never picked for a song unless it is the only clip.

What happens when a song starts depends on how many clips are ticked:

* **One**: it plays for the whole song, jumping to a random spot at every section change.
* **Several**: a random one starts the song, and the clip changes with the music. A drop, meaning a groove after an intro or a break, or a section led in by a beat-repeat, cymbal swell or gap, swaps the clip once at least 4 bars have passed since the last swap. An ordinary section boundary swaps it about one time in three, and only after 16 bars without a swap. Every other boundary is a jump within the current clip. The *switch between the ticked videos* checkbox in the Video tab turns swapping off.
* **None**: every clip in the folder is fair game, as if all were ticked.

Phone and camera clips are usually 4K H.264 or HEVC at 60 fps with an audio track, which is heavy to decode and, more importantly, slow to seek: the backdrop jumps to a new spot at every section change and swaps clips on drops, and an H.264 seek stalls the picture for 100 to 300 ms right on the downbeat. `gacha_transcode.py` brings the whole folder to a fast-seeking spec with the system's ffmpeg and ffprobe, no Python video package needed:

```bash
python3 gacha_transcode.py --dry-run      # what would change
python3 gacha_transcode.py                # 1080p, 30 fps, MJPEG .mov, audio removed
python3 gacha_transcode.py --height 720 --fps 24 --quality 4
python3 gacha_transcode.py --codec h264 --quality 20 --gop 15   # smaller files, keyframe every 15 frames
python3 gacha_transcode.py videos/field/clip.MP4                # just this one
```

Every video under `videos/` and its set folders is probed. Files already at spec are left alone, anything else is re-encoded next to itself and the original moves to `videos/originals/`, mirroring the set folder it came from. A file that only has an audio track to lose is remuxed without re-encoding. The stock clip and `originals/` are skipped, and `--force` redoes files already at spec.

Clips from the web go through the URL field under the Videos tab: paste a YouTube, Vimeo or any other page [yt-dlp](https://github.com/yt-dlp/yt-dlp) knows and press Fetch (`gacha_fetch.py`). yt-dlp runs as a subprocess on a worker thread, downloads the best picture up to 1080p as an mp4 into `videos/web/` (one video, never the playlist it sits in), and the file then goes through `gacha_transcode.py` so it seeks instantly, the download parked in `videos/originals/web/`. Progress lands in the Log tab and the clip appears in the tree when done. It needs `pip install yt-dlp` (in requirements.txt) and an ffmpeg to merge YouTube's separate picture and sound, the bundled one is enough; without `ffprobe` on `PATH` the transcode step is skipped and the clip is kept as downloaded, which plays fine at 1080p and only seeks slower. When a site changes and the fetch fails, `pip install -U yt-dlp` is the fix; nothing in the app needs to change.

MJPEG files are larger, roughly 5 MB per second at the default quality, but they live in the git-ignored videos folder. The folder is rescanned on Refresh, so new files are picked up without a restart, and everything in it except the stock clip is git-ignored. While a song plays, the video jumps to a random spot at every section change, so the picture cuts with the music. Turn that off with the Playback checkbox in the Video tab.

Below the song parameters, the **Settings** tab holds the live I/O, everything that connects the app to the world:

* **Audio output**: the app's audio stream. It opens at launch on the remembered device and every sound the app makes goes through it and through the racks (Audio FX): songs, the section engine, the live input. The devices are PortAudio's, from the platform's native host API: on Linux the `(hw:x,y)` entries are the cards themselves, exclusive and lowest latency, and one that PipeWire or another app is actively playing through cannot be opened (idle ones are released by themselves), while `pipewire` and `default` go through the desktop's routing, shared with everything else, at about 11 ms; the first launch picks `pipewire`. Windows lists the WASAPI devices, macOS CoreAudio. The status line shows the output peak, DSP load, buffering, the sync delay and any drops; when the device cannot be opened it says so, and songs fall back to Qt's media player, on the desktop's default output, with no racks and no stem switches, until the output can be opened. Changing the device or the block size reopens the stream, which stops a playing song. 256-frame buffers make about 11 ms of buffering plus whatever the devices add; raise the block size if the status line shows drops.
* **test round-trip**: the real latency, measured. Plug a cable from an output of the interface into the live input, turn its level up, stop any song and press the button: a 4 ms burst at 1 kHz goes out, the input is watched for a second, and the burst's position found by cross-correlation gives the round trip in milliseconds and frames, the device, its buffers and one processing block included, which is what a guitar through the app experiences. The live input is muted while the test runs so the cable cannot feed back. The result also lands in the log.
* **Live input**: tick it, or press `A`, and the chosen hardware input joins the stream: the live path of a show, where a VHS deck's sound reaches the PA through Gacha, through the *live* rack, alongside the sections and songs. It runs in `gacha_audio.py` on its own thread on two PortAudio blocking streams, one for the input and one for the output, with Python between them owning every sample; the blocking calls sleep while they wait, so the stream costs a few percent of a core (pedalboard's streams, used before, busy-looped and burned a whole core). The main volume slider sets the stream's level, ramped so it never clicks. **Sync** holds the live input back by a settable number of milliseconds so it meets the picture, which arrives late: the grabber hands over a frame one frame period after it happened (40 ms on a PAL MS210x, measured from the kernel's capture timestamps), the paint loop and its 25 ms effect throttle add a dozen more, and the screen or projector adds its own. Set it while watching a tape, on mouths and cuts; it changes live without a click. With the video input on, the status line also shows the picture's measured capture latency as a starting point for the sync value. The input choice and the tick are remembered, so the show's setup comes back at launch.
* **Stats**: *stats on screen* puts a small readout in the top right corner of the picture that stays with the interface hidden: the backdrop's paint rate and GPU time, the video's frame rate and size, the machine's CPU load and this app's share, the app's memory with the takes' part, what is left on the machine, and with the audio stream open two lines on the audio: the driver mode and the input and output peaks, then DSP load, buffering, sync delay, late rounds and xruns (input overflows / output underruns), plus a line on the playing song (position, which stems are in, A/B) or the running section. Under those, three lines always: the live clock (bpm, the length of a bar and of a beat), what the next `N` would render (the kind, 8 bars and their length in seconds, the drum style, and the style a random pick landed on for the section playing now), and the song-only structure settings of the Generate tab (intro style and cap, outro style, bars and tail, section lengths), which a live section only borrows from: it is always 8 bars, and the intro and outro styles shape the live kinds of those names. CPU and memory need `psutil`.
* **Video input**: pick a V4L2 capture device, a webcam or a cheap USB composite grabber with a VHS deck on it, and the live picture replaces the clips as the backdrop. The **mode** next to it lists the frame sizes and pixel formats or codecs the driver offers (read with ffmpeg, largest first) and reopens the device with the one you choose; *default* leaves it to the driver. A VHS grabber wants its native 720x576 (PAL) or 720x480 (NTSC) raw mode, and a webcam's mjpeg modes cost less to decode than h264 at the same size. The choice is remembered. The effects and the shader layer run on it as usual; clip switching and jumps are held off until the input is set back to off. Rewinds work on the live picture too: the last seconds of captured frames stay in memory, a rewind scrubs back through them and then fast-forwards back to live, a backwards-then-forwards jog. The list is read at launch. A **second** device (a webcam next to the VHS grabber) goes in the row below, with its own mode: both are kept open at the same time, two decoder threads. **second on B**, the `W` key or the `video_second` MIDI button in the picture group puts the webcam on the B side of the A/B pedal, where the section's take frames go otherwise: the pedal at 0 is the tape, at 100 the webcam, with the Picture row's dissolve (mix, add, screen) between, and it works with no section playing as well as under one, in all three picture modes (a burst still throws its frame over the picture). Since the webcam brings no sound, the pedal then leaves the tape's audio whole and only brings the section in over it, instead of the usual equal-power crossfade. Off, B is the take frames again; with no second device chosen the tick does nothing but say so in the log. The two must be different devices. Takes record the first input either way. Like the take frames, the B layer is drawn by the OpenGL backdrop only.
* **Audio analysis** (VJ mode): tick it, or press `L`, and an audio input drives the visuals instead of a song; with the live input on, it listens to that input. Pick the capture device (a mic, a line in, or on PipeWire/Pulse a monitor source that carries whatever the machine is playing); the level bar shows the loudness the effects see, normalised against a slowly decaying running peak so quiet and loud sources both use the full range. With **auto** ticked (the default) the app listens along: after about 4 s it has a tempo, from spectral-flux onsets autocorrelated under a tempo prior, locks the beat phase to the bass onsets so kicks rather than offbeat hats mark the beat, and follows the root note as the dominant pitch class of a running chroma from 30 Hz up, which is what the tint effect uses. The status line shows what it hears. Tap tempo is the fallback and the override: press `T` on the beat four or more times, the first tap on the one, and auto switches off and follows your taps; `D` restarts the bar on the current tempo and the spinbox can be typed into as well. These controls (the bpm box, Tap, Downbeat, Ableton Link) are the Settings tab's **BPM** row: there is one tempo in the app, the live clock, which runs the visuals, the racks' delays and the section engine whenever no song plays, is what Generate renders at unless *random* is ticked (then 60 to 180, rolled per song), and takes a playing song's tempo when one starts, so the box always shows what sounds. **Ableton Link** (the *Link off / on* button in the BPM row, right of *random*, remembered, also a MIDI button in the *clock* group) makes the live clock a peer of the Link session on the network: switched on it joins whatever session is there and takes its bpm (Link's rule: the session already running wins; alone, the app's tempo is the session's), and from then on typing in the bpm box, tapping `T` or a playing section changes the bpm for everyone, Live, Traktor and the drum machines included, as their tempo changes reach the box here. Start/stop is shared as well (Link's start/stop sync), for the Perform tab's section engine only, never for songs; the *▶* / *■* button right of it (MIDI row *link_play* in the clock group, shows what a press sends: play while the session is stopped, stop while it plays) sends play and stop to the session by hand, and the app then follows them like any peer's press: a peer pressing play starts the current section again, the one that played last, as it was, nothing new is rendered (with none yet the log says so and waits for `N`); a peer's stop stops it on the bar like `Shift+N`; and a section starting or stopping here (`N`, `Shift+N`, a break) starts and stops the peers, Live from its own bar. A section started from silence with peers in the session waits for the session's bar and starts on it to the sample (silence inside the audio block up to it; seen less than a quarter beat after the bar, as a peer's play is, it enters the loop that far in instead of waiting a bar), and the live clock's bar is anchored on it, so the visuals are on Live's bar too; alone in the session the start is immediate and the session's bar is moved to it, so peers joining later share our bar. While on, the button itself shows the session's beat (*Link 1* to *Link 4*), refreshed 20 times a second, a label's text, nothing the machine notices, and the status at the end of the row shows how many peers are in the session, the session tempo and whether it plays. Once a section loops, its bars are the clock's own (`D` and the taps' downbeat are not sent). Auto mode's tempo and beat following stand down while Link is on (the root note is still listened for). It needs `aalink` (`python -m pip install aalink`, in `requirements.txt`); without it the button is greyed out. `X` marks a drop by hand: the flash and the shaders' `iDrop` fire, the bar restarts on it, the look and the shader roll again and the clip may switch. Every 8 bars of the live clock also count as a section, so the look, the shader in random mode and the clip jumps keep changing the way they do in a song. Loudness, beat, bar, tempo, root and drop reach the shaders as `iLoud`, `iBeat`, `iBar`, `iBPM`, `iRoot` and `iDrop`; section stays groove and swells are not detected. Automatic drop detection from loudness is in the code but off, since on rendered songs it caught few real drops and fired falsely every half minute. Starting a song switches live off; the interface hides while live is on like it does for a song.
* **save set...** and **load set...**: a set is everything below the hardware in one JSON file (the `sets/` folder by default, the date for a name): every knob, tick and menu, the effect settings, the LFOs, the macros, the scenes, the M:C tab, the VST inserts, the takes' settings and the ticked samples and videos (by name, so the set loads wherever the files are). The sound card, MIDI, the Erae, Link and the video inputs are not in it, so a set from the studio loads on the show laptop as it is. Loading replaces the values and the pools with the file's at once, every tab following (the VST chain reloads, the shader layer is left as it is), and they are remembered for the next launch like any change; the hardware stays. The live knobs and switches are remembered too (every few seconds and at close, so a launch starts where the last one left off): the racks, the channel volumes, the master volume, the sync delay, the A/B, the video grade, the video effects' strengths, the shader, its blend and mix, the picture and the dissolve; not the voice switches, which start in, nor the VST knobs, the plugins keeping their own state with the inserts. A set carries them.
* **forget the values only...** and **forget every saved setting...**: two buttons next to them, each asking first. The first is a clean slate without touching the hardware, applied on the spot like a set: every knob, tick and menu, the effect settings, the LFOs, the macros, the scenes, the M:C tab, the VST inserts and the takes' settings go back to their defaults and the MIDI map to the stock one, while the sound card, the MIDI ports, the MIDI out, the Erae, Link, the video inputs and the ticked samples and videos stay. The second forgets everything Gacha remembers between launches and restarts the app. Files on disk (samples, videos, takes, renders, plugins) are never touched.

Everything about the backdrop lives in the **Video** tab of the parameter panel:

* **Playback**: jump to a random spot in the clip at every section change, switch between the ticked clips on drops, and hide the interface and the mouse pointer the moment a song starts. Move the mouse, click or press a key to bring them back, and they hide again after an adjustable idle time (default 1.5 s). When a song ends, every effect switches off, the interface comes back and the video keeps looping clean. `F11` or the button goes fullscreen and hides the interface at once, `Esc` or `F11` again leaves it. `Space` jumps to the next video FX: a new random effect look plus the next shader, or a random one in random mode. `S` switches the shader layer off and on; while it is off, `Space` only cycles the video effects. `C` toggles *video only*: the picture as it is, no effects, no shader layer, while the picture keeps following the song (timeline, section jumps, clip switches, rewinds, the outro fade). `1` to `9` select a shader directly in list order and `0` turns the layer off. None of these keys bring the interface back.
* **Video off** (`V`, a tick under *video only* in the Video tab, a MIDI button in the picture group, remembered): the whole picture goes, to save the CPU and the GPU on a night of sound only or on a weak machine. The clip's decoder and both capture devices are closed (so another program can take the grabber or the webcam), the 60 fps repaint stops and the window shows its background; the effects, the shader layer and the section's take frames cost nothing until it is off again, when what was chosen, the input and its mode, the clip, the second input, reopens as it was. Songs, the live input, the sections and the MIDI out are untouched. A take recorded meanwhile has sound only, since the frames come from the capture device. Different from *video only*, which keeps the picture and drops the effects.
* **Source grade**: colour correction of the picture itself, made for the VHS input: **exposure**, **black** level (negative pulls the tape's grey blacks down), **gamma** for the mid-tones, **contrast** around mid grey, **saturation**, **warmth** (amber to blue), **tint** (green to magenta) and **sharpen**, from -10 to 10: positive is an unsharp mask against the four neighbouring source pixels, at the tape's own resolution, that lifts the detail a VHS deck or a soft grabber blurs away (0.3 to 0.8 is a gentle lift, 10 is pure grit); negative is a blur, a 3x3 box that widens up to 10 source pixels, so one knob runs from smear to razor. Every knob has a MIDI row in the Controls tab. It runs on the GPU inside the video sampler, so it sits before every effect and the shader layer and stays on in video-only mode and clean flashes; the *neutral* button puts everything back. **react** lets the grade breathe with the music, very slightly: at most a few percent of exposure and saturation with the loudness, and a touch of warmth toward the root note's colour (notes on the red side of the hue circle warm the picture, those on the cyan side cool it). Meant for MIDI knobs later.
* **Takes**: press `R`, or the record button (the Takes row of the Perform tab, above the section buttons), and the live feed is recorded into RAM: the tape's dry sound from the live input and the frames from the video input, starting with a **pre-roll** of the seconds before the press (0 by default, up to 12, remembered between launches), because you decide something was interesting after it happened. Press again to stop. A **limit** (60 s by default) stops a forgotten take; the next press then starts a new one. The takes together are the sample bank the engine will build sections from at the end of a piece, so short ones are fine, and all of them count. A minute of 720x576 frames is about 2.5 GB; the store is capped at 12 GB and the oldest takes go first. Each take remembers how far behind the world its frames were (the grabber's 40 ms), so an audio offset finds the frame that was on screen. The takes stay in RAM during the show: encoding them while playing glitched the sound, so nothing is written then. With **keep the takes** ticked in the Settings tab (the default, remembered), closing the app writes every take not yet on disk, by ffmpeg, as an MJPEG mov with the sound muxed in (pcm, offset by that lag) into `videos/takes_<date>/`, a set folder that shows up in the Videos tab, so tomorrow the takes are backdrops; a take without picture becomes a wav. A progress window counts them down and can be cancelled (the rest are lost). *save takes* in the Perform tab writes the ones not on disk earlier, between pieces, in the background, the log naming each file as it lands and the status line counting the ones still being written or not on disk yet; *forget last* (`Shift+R`, and a MIDI button in the *tape* group) drops the take being recorded, or when none is running the last one, from RAM, so a bad one never reaches the material (a file it already became stays); *clear* (`Ctrl+Shift+R`, a MIDI button too) forgets them all, a running recording included. `gacha_takes.py` is the store.
* **New random look on every section**: which stylistic effects are active and how hard is re-rolled every 4-bar phrase, and the section-level choices (kaleidoscope, mono tones, shader) change with each section, so long sections keep moving.
* **Effects**, each a strength from 0 (off) to 1, driven by the playing song's section map, root notes and loudness:

| Row | Effects |
| --- | --- |
| Color | **color** saturation and hue per section, intros bloom in, breaks wash out. **tint** toward the colour of the section's root note. **pump** brightness follows loudness. **flash** drop FX in sync with the audio: the frame freezes and stutters in the exact rhythm of a beat-repeat, builds to white under a reverse cymbal, holds still in a gap and inverts on the drop. |
| Pixels | **pixel** pixelation during breaks, switching on and off per 2-bar phrase with a new block size that breathes with the loudness. **bits** colour depth, 1.0 is 1 bit, 0.75 is 2 bits, 0.5 is 3 bits, 0.25 is 4 bits. **dither** 1-bit Bayer dithering. |
| Tone | **mono** grayscale where each section rolls its tone count: smooth gray, or black and white at a random threshold, or 3, 4, 6 or 8 tones, with strength setting how often the hard tones win. **solarize**, **edges**, **scanlines**. |
| Grain | **grain** film grain. **granular** the fragments' playheads: while a slice sounds as grains (the Perform tab's Fragments rows) the frame is that slice, and every grain is a lit band at its spot, as wide as the grain, swelling and fading with its window, with a bright playhead line crossing it as it reads (backwards for a reversed grain); the motion scatters the bands, the size widens them, a frozen playhead (speed 0) holds the frame, the frame darkens a little outside the bands; the pitch is not shown. With no fragment sounding, five made-up bands run on the rows' settings at the knob's strength, so the tick shows something idle. |
| Motion | **zoom** punches in with loudness. **trails** bright parts linger. **glitch** horizontal tears, more when loud, a few bands at a time. Each section picks a flavour: thin sharp lines of 0.4 to 1% of the frame height, medium bands of 4 to 14%, or anything from 4% up to 38% slabs. **rgb shift** chromatic aberration pulsing with loudness. **reverse** rewind: on a downbeat, with probability = strength, the video runs backwards for the chosen **length** (1/8 bar by default, up to 2 bars, or random per bar) at a random speed from 1x to 3x; every clean flash jogs the same way, and a reverse cymbal swell rewinds the picture faster and faster into the drop. This is a real rewind of the video, at full resolution and any speed, and playback carries on forwards from wherever it stopped. It is instant on the all-intra files `gacha_transcode.py` writes; long-GOP camera originals decode a whole keyframe group per step, which is fine at 1080p and too slow to keep up at 4K, so transcode those. |
| Frame | **vignette**. **kaleido** upright kaleidoscope with 4, 6 or 8 mirrored segments; strength is how often a section gets it. **clean** on a downbeat, with probability = strength, a 1/16-note flash of the video as it is: no effects, no shader layer. |

The Randomize button rolls new strengths for all of them.

**Rendering.** On a machine with OpenGL 3.3 the backdrop is drawn on the GPU (`gacha_gl.py`): every effect above runs as a fragment shader at full resolution and 60 fps. Without OpenGL the GUI falls back to a numpy renderer that shrinks frames to 480 pixels wide.

**Shader layer.** On top of the video, a second layer runs a generative fragment shader from `shaders/`, composited with its own opacity and blend mode (mix, add, screen). The layer starts off when the app launches and switches to "random" as soon as a song has been generated; "random" picks a new shader every section. The shaders are Shadertoy-style: write a `mainImage(out vec4 fragColor, in vec2 fragCoord)` and you get `iTime`, `iResolution`, `iChannel0` (the processed video) and `iChannel1` (the shader's own previous frame), plus the music: `iLoud` (0-1), `iBeat` and `iBar` (phase 0-1), `iBPM`, `iSection` (0 intro, 1 groove, 2 break, 3 outro), `iRoot` (0-11, -1 unknown), `iDrop` (1 on a drop, decaying), `iSwell` and `iSongPos`. The alpha you output is the layer's coverage. A shader that only works by replacing the picture can put `// gacha: opacity=1.0` in its source to override a lower layer opacity. Nineteen originals ship:

| Shader | Look |
| --- | --- |
| `bars` | Stage-light bars sweeping in, one per beat. |
| `datamosh` | Fake codec corruption, blocks stick and drift, a drop resets. |
| `feedback` | Zoom feedback toward the viewer, bright parts leave straight trails. |
| `glow` | Bloom on the bright parts, pumping with the beat. |
| `glyphs` | The picture rebuilt from procedural glyphs, refreshed per beat. |
| `halftone` | CMYK print screens, rotating slowly, negative on a drop. |
| `leaks` | Light leaks from the edges on each beat, in the frame's own colours. |
| `lanes` | One narrow vertical lane of the picture, a few pixels wide, repeated across the whole screen: a barcode of one of its own columns. A new random lane every beat, wider when loud, broad stripes on a drop. Replaces the picture (opacity pinned at 1). |
| `mirrorhall` | Mirror wall: full-height panels each showing a different slice of the picture, one lighting up per beat. |
| `mosaic` | Tiles that shift, mirror and flash, 45 to 220 of them with loudness. |
| `plasma` | A fractal field in the video's own colours, breathing with the beat. |
| `pointcloud` | LiDAR-style dot cloud with parallax and a scan line per bar. |
| `relief` | Embossed heightfield lit by a light orbiting once per bar. |
| `slitscan` | A slit sweeps per bar and freezes time slices behind it. |
| `strips` | A vertical strip of the picture about 100 px wide, full height, tiled side by side across the screen: one slice of the frame in columns. A new random strip every beat, wider when loud, a third of the screen on a drop. Replaces the picture (opacity pinned at 1). |
| `sparks` | Particles born on bright pixels, drifting up. |
| `super8` | Super 8 home movie: the picture changes 18 times a second, faded Kodachrome colour with red halation, grain, dust, hairs and dark scratches, flicker that grows with loudness, splices and orange flash frames on downbeats, a swell browns the lamp, a drop is the reel running out and burning. |
| `thermal` | Heat palette with animated iso-lines, cold in breaks. |
| `vhs` | A tracking band rolling up the full height every 2 bars, frame roll and wobble top to bottom, chroma bleed, dropouts on the beat, wearing out toward the end. |

Keys `1` to `9` reach the first nine in this alphabetical order; the combo and `Space` reach them all. Compile errors show in the render log. Shaders you bring in from elsewhere keep their own licence.

### Perform

(A practice sheet for a whole set, scene by scene with a MIDI map to learn: [PERFORM.md](PERFORM.md).)

The Perform tab is the live section engine, what the feet drive on stage: every control has a key and a MIDI binding (Controls tab). The four **stems** (`F1` to `F4`) gate the section engine and a playing song alike, after their racks. It needs the audio output open (Settings tab), because the section is mixed into that stream; with it closed N says so in the log. **Material** is what sections are built from: the takes recorded during the show, or the ticked samples while rehearsing; the ticked videos' soundtracks join them when *Video audio* (Video tab) is on, and are the material on their own when no sample is ticked. Only what is ticked is used: nothing ticked anywhere means no material, and `N` says so. **next section** (`N`) renders an 8-bar loop from the material at the live tempo, `gacha_section.py` doing in about a second what the engine does for a song, and starts it on the next bar; while it loops, the following one is rendered ahead, so the next press is instant. A section carries the song's sub bass too: its root is read off the layers (chroma), and one sub note per bar sits on the first kick, into the drums stem, with the Generate tab's *Sub bass* and *Sub notes* knobs. The whole Generate tab is read at each press of `N` (drum gains, chances, layers, pans, drum style...), so a kick turned down between two sections lands on the next one: the section rendered ahead is dropped and rendered again half a second after the knobs stop moving (the log says so), so the press still lands at once; the status shows the root, and the shaders' tint follows it when the pedal is on the section's side. On the Sections page a faint ♪ after a row's name says only the generated songs use it (the intro length, the section lengths, the fades, the drop FX, the break chance, the synth; on the Settings page the song duration, the seed and the samples count, and the BPM row's random tick says so in its tip); everything unmarked the live render reads at `N` as well. A row that mixes both marks the song boxes' own labels, and the legend sits by the Randomize button. **next kind** picks the shape: groove, break, build, sparse, random (one of those four), **intro** or **outro**. An intro is 8 bars shaped by the intro style (random, or ambient, sparse, build, drums-first, filtered, reverse-swell, collage), the songs' own intro code on the live material; it loops like any section, so a reverse swell crescendos into the loop's end and N on its last bar is the drop. An outro is a groove whose ending effect (the outro style, random picks one; its tail, bars, wet and amount from the Generate tab) blends in over the last bars of a shorter body and rings out to silence inside the 8 bars; it is entered at bar 5, so an outro is four bars from N to silence, and the sections stop by themselves on its last bar, like Shift+N. The **Shapes** row at the top holds the **intro** style, the **outro** style and the **drums** style, each the Generate or Sections tab's own box again, the pairs one setting by name, except that the Perform copies have no *none* (a live intro or outro always has a shape; the Generate tab set to none leaves the Perform box where it was, and the live render reads the Perform box). The meter's big line reads kind and style, root, tempo, the drum style the playing section was patterned in, and *next ready* or *rendering next...* when that is the state. **stop / start** (`Shift+N`) silences the section on the bar; the tape stays. Pressed again with no section playing it starts the last one over, as it was, without rendering anything; with Ableton Link on this is the session's stop and play, both ways (see the Settings tab's Link). **event** (`E`) fires a one-shot cut from the material on the quantize grid (below). **burst** (`B`) is the raw version: a slice of the material from a random spot, on the grid too, at the tape's own level and heard whatever the A/B pedal says (it goes through the events rack and the F4 switch, not the crossfade); the frame it was cut from takes the whole picture while it sounds, at least two screen frames, from the moment the sound starts. **length** sets the slice, 10 ms to 1 s, remembered; as a MIDI knob it sweeps on a log scale, 100 ms halfway. Two **breaks** end a section the way a generated song runs up to a drop, on the phrase: the loop is two 4-bar phrases, and pressed anywhere they wait for the phrase's last bar, bar 4 or bar 8 (the status says which), then the section is taken over for that bar, and the next section (the pre-rendered one when it fits) drops in on the one, the loop's middle or its end; pressed inside that last bar they run from the next beat, a beat at the least. **glitch** (`G`) throws sixteenths of the bar that was playing about, some backwards and some stuttered, a roll on the last beat, a sixteenth of silence before the bar; the picture follows the slices. **break** (`Shift+G`) is the song's own transition: a beat-repeat of the bar's first slice (accelerating, steady or halving), a reverse cymbal swell rendered with the section from the kit's ride (or half a second of the material) rising under it, half a beat or a beat of silence right before the drop. **gap before the drop** next to them is that silence (and the glitch's sixteenth): unticked, the roll and the repeat run straight into the one. Remembered, off by default. With the *flash* effect on, the picture does what it does in a song: it stutters and inverts with the beat-repeat, freezes in the gap, builds to white under the swell and inverts on the drop; in live mode the drop also counts as a drop for the clock and the clip. With no section playing either is plain next. **repeat** (`H`, held) is the drum machine's roll over the running loop: the cell of the bar playing at the press loops for as long as the key or the MIDI note is down (a CC pedal holds it above 64), and the section runs on underneath, so letting go lands exactly where the loop would have been; the let-go itself waits for the next bar of the loop, the cells rolling until then, so the roll always ends in time (at once with the quantize grid off), and a press again before the bar keeps the hold and its anchor; a queued section, the clock and Link are untouched; the on-screen button latches it for the mouse. The **division** next to it is the cell: the bar, 1/2, 1/4, 1/8, 1/16, 1/32 or 1/64 note (a pitched buzz by then), `-` one finer and `=` one coarser, or a MIDI knob from the bar at the bottom to 1/64 at the top. Finer while held tightens the roll from the same one, the classic run into a drop; coarser widens it to the cell containing it. The cells sit on the bar's own grid, so every retrigger lands in time and a change of division or position is heard at once, in time. **position** moves the window: 0 is the cell captured at the press, each step one cell of the current division earlier or later, round the loop's ends (`,` and `.`, or a knob with the captured cell in the middle and 16 cells either way). **reverse** (`/`) plays the cell backwards. The division is remembered, the position and the direction start at 0 and forwards. The bar meter draws the window in yellow over the bars (in two pieces when it wraps round the loop's end), with the cell's own playhead in white and a chevron for the direction, the red sweep underneath still showing where the loop will land. The picture shows the cell's frame on every hit, and with the *flash* effect on it stutters the way it does under a break; the MIDI out gets the cell's drum hits on every repetition, backwards when reversed. A glitch or a break landing while a repeat is held takes over (the repeat comes back on the drop if still held), a new section arriving on the bar keeps it running on the same cell of the new one, and a stop ends it. The four **stems** (`F1` to `F4`) switch drums, layers, chops and events in and out with a ramp, on the grid. The **Drums** row is the kit voice by voice: kick, snare, closed hat, open hat, ride, the hat stutter and the sub bass each have a switch (`Shift+F1` to `Shift+F7`, lit while in) and a solo (`S`, `Ctrl+F1` to `Ctrl+F7`; while any voice is soloed every other one is out). A section is rendered as one stem per voice, so a voice out is gone from the sound (and from the MIDI out as well when *follow mutes* is ticked there; by default the notes keep going and the drum machine does its own muting); its rack in the Audio FX tab sits before the switch, so a delay or a reverb on it rings out after the mute, the dub move. *all voices in* (`Shift+F8`) puts every voice back, clears the solos and cleans the voice racks (effects off, volumes at 1): the panic button before the next scene. Every voice starts in at launch, never remembered. **Quantize** is the grid all of these land on while a section plays: off (at once), or the loop's next sixteenth, eighth, beat, half bar or bar; it holds the voice and stem switches, the solos, `E` and `B`, so a mute pressed a little early lands on the eighth and a burst hits the grid. Remembered; the MIDI button *quant_next* steps through it. With no section playing everything is at once. The **A/B** slider (`[` and `]` step by 10) mixes the tape through against the section at equal power, 0 to 100 %; an expression pedal drives it through the `ab` row of the Controls tab. With the video input (Video tab) off there is no live picture on A, so the slider goes to full B on its own, at start and whenever the input is set back to off. **Picture** (a row of the Video tab, under *picture follows*) chooses what the screen shows while a section plays: *follow* dissolves the picture from the tape to the frames the sounds were cut from (takes with video) as the pedal moves, so the picture and the sound cross over together; *take* and *live* pin it to either side. Between two sounding events, at the loop's seam and through a break's gaps the last frame is held, so with the pedal on B the tape never flashes through (takes with sound but no video are the one exception: nothing to hold, the tape stays). The tape under all this is a ticked video when no live input is on: a section started from silence picks one the way a song does (a random one of the ticked clips, never the stock one), every 8 bars count as a section for the picture so the clip may switch on those boundaries or jump, and the drop at the end of a break swaps it after 4 bars, all with the Video tab's Playback ticks. **dissolve** next to it says how the two pictures meet on the way: *mix* is a plain crossfade, *add* and *screen* lay them over each other, at full strength when the pedal is halfway (add clips bright on bright, screen never clips); all three are the tape alone at 0 and the take alone at 100, so the picture stays in step with the sound. The dissolve happens on the GPU before the effects and the shader layer, so they see one picture. The live clock follows the section, so the visuals, the shaders and the tap tempo are on its bars, and with Ableton Link on the session hears the section's tempo as well. The **Speed** rows are the deck's transport tricks, all over the running loop with the bar, the clock, Link and the MIDI clock untouched. **half time** (`Shift+H`) and **double** (`Ctrl+H`) run the bar at half or double speed from its start and jump back to the transport every **sync** (half a bar, 1, 2 or 4 bars, or the loop), Gross Beat's way, so a half-time bar is its first half slowed down and a double-time bar is this bar and the next inside one; they land on the quantize grid, never remembered. **pitch** says what the pitch does under them, under a nudge and under a tempo change: *follows* is varispeed, the Looper's way, half time an octave down, double an octave up; *locked* keeps the pitch with a granular stretch (WSOLA, grains of 21 ms lined up by correlation; the drums smear a little at half speed), the warped clip's way. **tape stop** (`Shift+B`, held; the button latches it) is the brake: from where it caught the transport the section decelerates to a stop over the length next to it (1/4 bar to 4 bars), the pitch falling with it, and let go it spins back up over the same slope, then the transport, which ran on underneath, is heard again on the grid; it always drops in pitch, that is the point, and it wins over the gears, a break over both; the repeat composes with all of them (a roll at half speed). **nudge −** and **nudge +** (`J` and `K`, held) run the section a few percent slower or faster (the amount next to them) and the live clock with it, so the shaders, the LFOs and the MIDI clock slide too: the DJ's pitch bend, to line up with a tape or a drum machine on its own clock; not under Link, which owns the beat. A **tempo change** while a section plays, the BPM box's or a Link peer's, is followed at once at the new rate (at pitch when locked) without a render, and the next section is rendered at it. The picture follows the head: the take frames the sound was cut from slow and freeze with a tape stop and run at half or double speed with the gears, a file on the tape side runs at the head's speed (the live input cannot), and the effects' clock, the shaders' beat and the strobes slow and stop with it; the LFOs stay on the bar. The MIDI out's hits follow what is heard (slower under half time, none while stopped), the MIDI clock follows the transport. The meter's sweep shows what sounds. Every control is a MIDI row (Controls tab, section engine group): half, double, pitch_lock, brake (held), nudge_down and nudge_up (held), and the sync and the tape stop length as knobs. The **Fragments** rows are Bitwig's Sampler in Sliced mode playing Fragments, over the section that loops (`gacha_frag.py`): the bar playing is cut into **slices** (4, 8, 16 or 32 equal pieces, 16 by default), and a slice held sounds as a cloud of grains read from it in place of the section, which runs on underneath, ducked by the voice's envelope, and comes back as the release fades; it goes through the same stems, so the racks, the voice switches and `F1` to `F4` apply to it as to the section, and the MIDI out's hits pause while it sounds. **fragments** (`F`, held; the button latches it) holds the **slice** picked next to it: *follow* is the slice under the playhead at the press, the sampler's way of playing what is there, or a fixed one; the Controls tab's *fragments* group has a MIDI note per slice, `frag_1` to `frag_16`, for a pad per slice (up to four slices at once, the newest stealing the oldest). A voice's playhead runs through the slice at **speed** (100 % the section's own, 50 % half time at pitch, 0 frozen on the spot, a drone of that instant, negative backwards) and at the slice's ends loops round, bounces or stops there (**play**: loop, ping-pong, once). Grains start from it every **rate**: *dense* is eight of them overlapping whatever the size, a cloud; a beat unit starts one on every such line of the bar's grid, in time with the loop, so a 16th rate with 16th grains is the slice stuttered on the grid and a 16th rate with 64th grains a rhythm of blips, the hypnotic rhythms. Each grain is **size** long, a fraction of the bar (Bitwig's beat units, a 16th by default), so a tempo change keeps them in time; it lands up to **motion** grain sizes from the playhead either way at random, and that far across the stereo field (0 is the slice replayed as it is, 100 % a smear, 800 % the whole slice as a cloud); it reads at **pitch** (two octaves either way, the playhead's speed untouched), forwards, backwards, at random or in turn (**dir**); each grain is triggered **repeats** times over, the same spot and place, for a roll; and its window is morphed by **shape** from a pluck through a Hann to an open one. **A**, **D**, **S**, **R** are the voice's envelope, gated: attack on the press (the section fading out under it), decay to the sustain, release on the let-go (the section back). Every row is remembered; the knobs are MIDI knobs and LFO, macro and scene destinations, *dir* and *play* MIDI buttons that step them. What keeps a voice smooth when the playhead's speed and the grains' pitch disagree (half speed at pitch, frozen, backwards): each new grain of the same pitch and direction is lined up with the last by correlation within 5 ms, over the stems summed, so the grains add in phase instead of combing at the grain rate. The *granular* video effect (Video tab) is the picture's side of it: the grains as playheads over the slice. The first granular, a cloud over each rack channel's last seconds, is kept in `attic/granular_cloud.py`, wired to nothing. The **Freeze** row under it is one button on the master (`gacha_freeze.py`): **freeze** (`Z`, held; the button latches it) holds the whole mix as heard, the tape through, the section, the song and the bursts after their racks and the sync delay, on the instant of the press: the last seconds of the mix sit in a ring, its write head stops, and that spot is played as grains lined up in phase by correlation (the WSOLA trick of the fragments), a clean drone of the moment; the live mix fades out under it over **A** while the transport runs on, and on the let-go comes back over **R** right where the loop is, so the tape never has to catch up. **size** is a grain (20 to 250 ms), **smear** 0 to 100 % jitters the spot up to half a second back, detunes a little and sprays the stereo, and past half adds octave and fifth scatter and reversed grains, a cloud; **pitch** shifts the drone two octaves either way. The picture holds the frame of the press (the shader layer keeps moving), and with the *granular* effect on it draws the frozen grains as bands near the right edge; the MIDI out's hits pause while it holds. Every knob is remembered, a MIDI knob in the section engine group, an LFO, macro and scene destination. The **metronome** (Controls tab, the MIDI out panel's *click* row; `gacha_metro.py`) is a click on every beat into the mix, higher and louder on the one: on the playing section's own beat grid, through the gears and a tape stop, the grid the MIDI clock follows, or on the live clock (tap, downbeat, the BPM box, Link) with nothing playing; with the MIDI out port open every beat also goes out as a note on the notes' channel, under the same lead as the hits: the one as the **one** note (76 by default, the GM hi wood block) at velocity 127, beats 2, 3 and 4 as the **beats** note (77, the low wood block) at 90; either set to off sends none for those beats. Remembered; a MIDI button, *metronome* in the section engine group.

### Audio FX

The Audio FX tab is the live rack: five channels, the **live** input through and the four generated stems (**drums**, **layers**, **chops**, **events**), each with eleven effects and a volume, and under them seven more, one per **drum voice** of a section (kick, snare, closed hat, open hat, ride, hat stutter, sub bass), the same eleven effects and a volume each, so a delay on the snare alone, a pitched kick or a crushed hat is one knob. A voice's column head is its switch, the same as the Perform tab's. The voices are summed after their racks into the drums channel, so the drums rack is the kit's bus and its knobs still shape the whole kit; a section arrives as its voices, a generated song as the four stems (its drums go straight to the drums rack), so the same knobs shape the show and the rehearsal. Every knob runs 0 to 1, and a MIDI CC spreads its 0 to 127 over it: **0 is bypassed** and costs nothing, a small value adds a little of the effect on top of the dry sound, **1 is fully wet**, the dry sound gone and only the effect left (a reverb wash, only repeats, the filter closed). All effects start off. The effects, in chain order: **highpass** (20 Hz up to 8 kHz), **lowpass** (20 kHz down to 150 Hz, resonance rising), **drive** (the engine's tanh saturator, gain-compensated so it gets denser, not louder, up to +30 dB into the shaper), **bitcrush** (16 down to 3 bits), **lo-fi codec** (a phone line: 3.4 kHz lowpass, 8 kHz sample-and-hold, 8-bit mu-law; pedalboard's GSM codec needs 40 ms blocks when streamed, this imitation has no latency), **chorus**, **phaser**, **pitch** (the one bipolar knob, -1 to 1: off in the middle, down to -12 semitones at the bottom, +12 at the top; a two-head delay-line shifter with 25 ms of latency and a tape-like warble, since pedalboard's shifter takes a second to start in streaming mode), **delay** (synced to the playing song's tempo or the live clock, a dotted eighth by default; the time and the feedback are settings, below), **reverse delay** (the typical pedal, `gacha_fx.ReverseDelay`: what goes in during the time is heard that much later backwards, its tail first; the reversed echo is fed back into the line, so the second echo is forwards again, the third backwards, the repeats alternating; the knob is the wet mix, only echoes at full; the time and the feedback are settings, below; a change of time crossfades over a block) and **reverb** (the knob the wet mix; size, damping and width are settings, below). **Volume** per channel is unity at 1 with a gentle taper below.

The racks run in `gacha_fx.py` inside the audio thread, block by block on pedalboard plugins streamed with their state kept, every amount ramped over the block it changes in so knobs never zip; with all eleven effects on a channel costs about 0.3 ms per 256-frame block. A song goes through the stream (open from launch) instead of Qt's media player: its stems file is read on a thread (48 kHz already, so no resampling; about half a second for a three-minute song), the player reports *playing* only once the sound actually starts, and the clip switch and the shader layer wait for that signal, so picture and sound begin together, its position is corrected for the output buffer not yet heard, and the transport, the section follow and the visuals see it as before, and the four stems pass through the stem racks and the `F1` to `F4` gates. The live input's share of the A/B pedal is applied after its rack, the section's before its racks, and a song is not under A/B at all. A safety limiter sits at the output. Renders made before the stems existed play as a single layer through the *layers* channel.

**Effect settings**: between two rules under the racks, what a knob does not say, one setting for every channel's rack (`gacha_fx.FX_SETTINGS`, read by the racks per block), a row per effect: the **highpass** and **lowpass** resonance (how much the ladder rings at the cutoff with the knob up) and drive (the ladder's input gain, 1 clean up to 10); the **drive**'s gain (the push into the shaper at full, 6 to 40 dB) and tone (a lowpass on the driven sound, 1 to 16 kHz); the **bitcrush**'s bits at full (1 to 12, down from 16); the **lo-fi codec**'s rate (2 to 16 kHz of sample-and-hold) and bits (3 to 12 of mu-law); the **chorus** rate, delay (short a flange, long a doubling) and feedback; the **phaser** rate and centre; the **pitch** range (the semitones at the knob's ends, 1 to 24); the **delay** time (1/32 of the bar up to a bar, following the tempo, 3/16 the dotted eighth, 1/12 a triplet) and feedback (0 to 95 %); the **reverse delay** time (1/64 of the bar up to a bar, a beat by default; a 64th is a buzz at the tempo's grain) and feedback (0 to 95 %, soft-clipped so it cannot run away); the **reverb** size, damping and width. Every one is a MIDI knob (Controls tab, the *audio racks: effect settings* group; a menu as a knob over its items), an LFO and macro destination and in the audio scene group; remembered.

**Master inserts (VST3)**: under the grid, a chain of third-party effect plugins on the master, after the five racks are summed and before the master gain and the limiter (so the limiter still protects the PA). Made for [plugdata](https://plugdata.org/), Pure Data as a plugin, for the final tweak of the sound in a patch, but any VST3 effect goes: a compressor, a reverb. The combo lists what sits in `vst/` (kept in the repo, contents ignored) and in the system's VST3 folders, vendor subfolders included (`Common Files/VST3/Xfer/Serum.vst3`), *browse...* takes one from anywhere; on Windows a `.vst3` in those folders is usually a bundle folder and the host only opens the DLL inside it (`Contents/x86_64-win/X.vst3`), which is done for you; **add** loads it at the end of the chain, a second or two for a JUCE plugin. Each row has its on/off (faded over one block), **edit**, **up**, **down** and **remove**; **bypass all** takes the whole chain out. The plugins run in the audio thread, in the app's own process, through pedalboard's plugin host: no extra buffer, no added latency beyond what a plugin reports, and that pedalboard compensates (plugdata reports 64 samples, one Pd block; its processing costs 0.04 ms per 256-frame block). The price of the in-process choice, taken for the latency: a plugin's editor window blocks this interface while it is open (the sound keeps running, so a patch can be tuned while listening; closing the app closes the editor with it), and a plugin that crashes takes the app with it. Eight **knob** combos point the MIDI rows *insert knob 1-8* of the Controls tab (group *master inserts*) at any parameter of any plugin in the chain; plugdata's `[param]` objects are those parameters, so a patch's own controls land on the pedals. The lists are live: a plugin that renames or adds parameters (plugdata when a `[param]` is put in the patch, Surge XT Effects when its type changes) is noticed within a second (a thread reads the names, plugdata exposes 2595 slots) and the combos are rebuilt; a knob left on a name the plugin no longer offers keeps its assignment, shown as *not a parameter now*, and works again if the name comes back. *master inserts off/on* is the bypass as a switch. The chain, its order, each plugin's on/off and its whole state (the plugdata patch lives in it) and the knob assignments are remembered and come back at launch. plugdata-fx prints a JUCE assertion line thirty times per block on Linux, so from the first plugin loaded the process's stderr is sent to /dev/null; Python's own messages still reach the terminal, the Log tab has the rest.

The **Video FX** tab is the pool: one tick per video effect (the twenty of the Video tab, *pixel* included), all off at first, and one per shader file, all on at first, for whoever cannot stand one of them (no more super8 look, ever). What is unticked is out of the show: an effect's strength counts as 0 whatever its knob says, the knob greys out in the Video tab and Randomize leaves it alone; a shader is left out of *random*, `Space`, the digit keys and the shader knob (which then run over the shorter pool, in list order) and only comes up when picked by name in the Video tab's combo; the ticks show at once: ticking a shader while the layer is off (the Video tab's combo) switches the layer on in *random* mode over the pool, so one tick alone puts exactly that shader on screen, with or without a song; unticking the one on screen (or the one the combo names) draws another from the pool, and the last tick to go takes the layer off. *all* / *none* under each group; the ticks are remembered. Every tick is also a MIDI button, group *video fx: the pool* in the Controls tab, next to the knob rows that already drive every effect's strength and the shader choice. The ticks work with nothing playing too: open the app, tick an effect (or hit its pad) and it runs on the looping clip at its knob's strength, on the tap tempo's clock, with a loudness that pulses on every beat (so pump, zoom, glitch and rgb shift move), the tint walking the circle of fifths one step per 8 bars and pixelate keeping the break's own rhythm, with no random look thinning it out and no automatic clip switching; only *flash* waits for a drop (`X`), which nothing marks while idle; a song or the live input then take over as usual. Three more buttons in the *picture* group put the clip in your hands: *video_prev* and *video_next* walk the ticked videos in the order of the Videos tab, *video_random* deals from a shuffled deck of them, so none comes again before every other one has played (reshuffled when the ticks change), never the one already on screen first. They work while a song plays as well, and the automatic switching counts its bars from the swap.

**Focused channel**: the Controls tab has, besides one row per channel and effect (55 knobs on MIDI channel 2 by default, and 77 more for the seven voice racks on channel 3), a second set of ten knob rows plus a volume that act on whichever channel was focused last, and twelve *focus* buttons to pick it (the five channels and the seven voices), so a controller with a handful of knobs still reaches every rack. The combo in the tab shows and sets the focus.

### LFO

Eight LFOs, one row each, over any knob of the Controls tab: a **destination** picked from the whole knob list (type into the box to search it: the list narrows to the names holding what you typed, any part, case blind; Enter takes the first, Escape keeps what was chosen; A/B, the main volume, the sync delay, the shader opacity and the shader pick, the nine grade knobs, every video effect's strength, all eleven knobs of the twelve rack channels, the eight VST knobs, the burst length, the repeat's division and position), so a random step on *shader pick* is a shader roulette per bar, a square on A/B a tape-to-section tremolo, a sine on a voice's lowpass the wobble, a random step on the repeat position a roll that jumps cells. The knob's own value is the **centre**: the LFO moves it around that and clips at the knob's ends, the knob wiggles on screen so you see it, and whatever sits under the knob (a rack, ramped per audio block so nothing zips, the picture, the mix) follows. Turn the knob, or move its CC, while the LFO runs and that is the new centre; switching the LFO off writes the centre back. **shape**: sine, triangle, saw up, saw down, square, random step (a new value each cycle, held), random smooth (the same, glided), random walk (a drift, each cycle a step from the last). **rate** is a cycle length in bars, 8 bars down to 1/32, on the live clock, which is a playing section's bars, Link's or the taps', so every LFO sits on the bar and in step with the others: a 1-bar and a 1/4-bar LFO meet on the one, and a tempo change keeps them on it. **depth** -100 to 100 %: in **±** polarity the knob moves half its range either way at 100 % (a centred knob sweeps the whole range), in **+** polarity it moves from its value upward by the whole range, an Elektron-style filter opening from where it sits; a negative depth flips the wave. **phase** 0 to 359°, so two LFOs on two knobs can run in opposition. **mode**: *cycle* runs free on the clock; *trig* restarts its cycle at a section start, at a drop (a break's end, or `X`) and at the *retrigger* button; *one-shot* runs a single cycle from the trigger and holds its end, an envelope (a saw up on a lowpass is a filter swell on every drop), holding its start until the first trigger. The bar at the row's end shows the wave right now. The rows are remembered as the stage setup, on states included: an LFO left on comes back on at launch, on the knob as it was left, and the knobs themselves are saved as you set them, never mid-wiggle (quitting writes the centres back first). In the Controls tab the *LFOs* group has a MIDI button per slot (off/on) and a knob per slot (the depth, 0 to 100 %, keeping the sign set in the tab), one *retrigger* button, and `Shift+L`, the panic: every LFO off and every knob back where you set it. The engine runs 100 times a second on the clock: fine for everything up to 1/16 bar; at 1/32 a sine gets a little steppy, a square or a random step does not.

### Scenes

Eight scenes, one row each: a snapshot of the live state, saved and brought back from a button. **save** keeps everything as it is at the press, in four groups: *audio*, the twelve racks and their volumes, the main volume, the sync delay, the A/B pedal, the burst length, the eight VST knobs and the inserts bypass; *voices*, the drum voices in or out, the solos, the stems and the quantize grid; *LFOs*, the eight LFO rows, on states included; *video*, the source grade, every effect strength, the shader, its opacity and blend, video-only, the picture mode and the dissolve. A knob an LFO is on is saved at its centre, never mid-wiggle. **load** brings back the groups the row **ticks**, so a scene with only *video* ticked is a look that leaves the sound alone, and one with only *voices* a drum arrangement. The switches (voices, stems, the shader, the LFO rows) flip at once, the voices on the quantize grid as always. The knobs land at once, or, with **morph** ticked, glide from where they sit to the scene's values over the time next to it, 1/4 to 32 bars at the live tempo, 100 steps a second (a rack knob is ramped per audio block under that, so nothing zips): only the knobs that differ move, an LFO on a gliding knob follows it as its new centre, and loading another scene mid-morph glides on from where the knobs are. The row says when the slot was saved and which scene is loaded; the status under the rows shows the morph's progress; a name is for the row and the status. Each slot's save and load, and the morph switch, are MIDI buttons (Controls tab, scenes group). The VST plugins themselves and the Sections tab (the next render's knobs) are not part of a scene. Everything is remembered.

### Macros

Eight macros, one row each: one knob over many. A macro has up to eight **destinations**, any knob of the Controls tab (the same list the LFOs pick from, typed into and searched the same way, the macros themselves left out, plus the eight LFO depths, so a macro opens an LFO: 0 to 100 %, the sign as set in the LFO tab), each with a **lo** and a **hi** as a percentage of that knob's range: as the macro goes from 0 to 100 % every destination runs from its lo to its hi, so a lowpass 20 to 90, a reverb 0 to 60 and a strobe 0 to 100 on one knob is a drop; a lo above hi runs the knob the other way (the main volume 100 to 0 under a filter opening). The ranges are typed in the list under the rows, for the macro picked in the combo (**edit** on a row picks it), or set by ear: dial the quiet state by hand, press **set lo**, dial the peak, press **set hi**, and every destination takes where it sat (a knob an LFO is on at its centre). A range changed in the list writes that knob at the macro's value now, so it is heard; picking a knob leaves it where it sits until the macro moves. The macro writes only when it moves, through the same path a scene uses, so the destination knobs move on screen and whatever sits under them follows; nothing runs on a timer. Last writer wins: a hand turn, a scene load or an LFO can move a destination in between, and the next move of the macro takes it back. A macro is itself a knob in the LFO list, so one LFO wiggles the whole list through its ranges, each knob its own way; and a scene carries the eight macro values in its *audio* group (the macro's knob comes back without writing its destinations, the scene carries those itself). The row shows the value and how many knobs the macro holds; the status under the rows the last macro moved. Every macro is a MIDI knob (Controls tab, macros group). Everything is remembered: the names, the ranges, the values.

### Controls

The Controls tab is the performer's map: every action, grouped as picture, tape, clock, section engine, mix and shader, source grade, video effects and the audio racks, with its key, what it does and its MIDI binding. It is built from one table in `gacha.py` that gives each action an id; the keyboard shortcuts and the MIDI bindings both hang on those ids, so a foot controller, a pad and the keyboard do exactly the same things. A held action (the repeat) is the one kind that listens to the release as well: its key is watched going down and up, its note's note off lets go, and on a CC the rise above 64 holds and the fall below lets go.

**MIDI inputs** lists every MIDI port the system sees; tick the controllers you play from, as many as you like (a foot controller for the sections and a drum pad for the events, say), and they all feed the same map. The list is rescanned every 2 s, so a controller plugged in during the show opens by itself; one that is ticked but not plugged in stays in the list greyed out. On the first launch every port except the ALSA *Midi Through* is ticked. Below the list, the last message received is shown with the port it came from, which is how you find out what a switch sends.

**MIDI out**: the drum hits of the playing section and song go out as notes, for a drum machine in another program to play them (Bitwig on a loopMIDI cable, a hardware sampler on the interface's MIDI out). The panel under the Erae row has the on/off (remembered, also the `midi_out` MIDI button in the section engine group), the **port** (the outputs the system sees, rescanned with the inputs every 2 s; the remembered one waits greyed when unplugged and opens by itself when it appears), the **channel** (10, the GM drum channel), the **lead**, the **gate** (note on to note off, 50 ms), *silence own drums*, and the **map**: one note per drum voice, kick, snare, closed hat, open hat, ride and the hat stutter (the glitch bursts), the General MIDI percussion notes by default (36, 38, 42, 46, 51, 44), each settable or *off*, *GM* puts them back. Tick **Model:Cycles** when the receiver is an Elektron Model:Cycles: the channel box gives way to the box's six track channels, kick on 1, snare 2, closed hat 3, open hat 4, ride 5, hat stutter 6 (its default T1-6 IN channels, RCV NOTE on), and since a note on a track channel plays that track chromatically the map becomes the pitch of each track, *M:C* puts the root note C4 (60) everywhere, the pitch the box's own pads send (a fresh tick does that by itself when the map is still GM). Notes, quirks and the rest of the box's MIDI surface are in `MODEL_CYCLES_MIDI.md`. The **sync** row has the two ticks any MIDI-synced gear wants: **MIDI clock** sends the 24 ticks a beat on the same port at all times, at the live tempo while nothing plays and, while a section plays, pulled onto the section's own beat grid (a tenth of a tick per block at most, so no tick doubles or drops) under the same lead as the notes, so the receiver's beat sits on our hits; **start / stop** sends Start half a millisecond before the tick on a section's downbeat when it starts from silence (entered late on a Link bar, on the next bar), so the receiver's step 1 is our bar 1, and Stop when the sections stop on their bar or the port closes. The status under them shows the tempo the ticks say, their count, and running or stopped. On the Model:Cycles that is SYNC > CLK IN on; it takes clock and transport together. The hits carry the pattern's velocity (humanised), and a section's are under the A/B pedal like its sound: velocity by the pedal's share, nothing at A; by default every hit goes out whatever `F1`, the voice switches or the solos do here, the receiver muting its own tracks; with **follow mutes** ticked they take the notes out with the sound, from the frame the switch lands on (the notes already handed over for the lead's window, a few milliseconds, are the exception). A song's go out at full. The **lead** is what makes two programs land together: a section is rendered before it plays, so every hit is known ahead, and each note leaves *lead* ms before the moment our own hit is heard (the block's start plus the driver's output latency), from a sender thread that sleeps to within 2 ms of the moment and spins the rest, within about 0.1 ms whatever the audio block size; set it to the receiver's output latency (Bitwig prints it in its audio settings) and its drums sit on ours, negative sends late. The one hit that cannot be early is the very first of a section started from silence, sent at once. A break sends what it plays: the retriggered slices' hits again at each repeat, reversed slices backwards, nothing in the gap, and the next section's from the drop. With **silence own drums** ticked our six drum voices are muted while sending, the sub bass staying, so the receiver's kit replaces ours instead of doubling it. Everything is remembered. The hits' velocity is the seventh field of the event lists (`[t, src, off, dur, rate, role, vel]`) the sections and the renders' JSON carry; renders from before have six and are sent at full velocity.

**Model:Cycles tab (M:C)**: the box's sound from Gacha, over CC on the MIDI out's port (the port open and aimed at the box, RCV CC on in its FILTER menu). A grid with a column per track of the box, T1 to T6 on MIDI channels 1 to 6, each headed with the drum the Model:Cycles tick sends there, and a row per parameter the box takes over CC (Appendix A of its manual, `MODEL_CYCLES_MIDI.md`): the **machine** (kick, snare, metal, perc, tone, chord, and the sampler of the Model-TG firmware the box runs), **pitch** in semitones (the box slews a CC jump into a glide, a firmware quirk), **decay**, **color**, **shape**, **sweep**, **contour**, **vol + dist** (60 clean, above it distorts), **pan**, the **delay** and **reverb sends**, the track **level**, **chance** and **swing** (they shape the box's own pattern, our notes always play), the **punch**, **gate** and **mute** switches, and the box's LFO: **speed**, **mult** (x the tempo, which follows our MIDI clock when it is sent, or a fixed 120 BPM), **fade**, **destination**, **wave**, **phase**, **reset** and **depth**. Below, the box's **delay time** (in 128ths of a whole note, following the tempo) and **feedback**, the **reverb size** and **tone**, on the **FX channel** box (the box's FX IN channel, 9 by default here). A change goes out as it is made; CCs are gathered for a couple of milliseconds and leave together, one value per controller and no more than one every 10 ms each (the DIN wire takes a millisecond per message; an LFO on a knob would otherwise drown the notes), and a value the box already has is not sent again: **send all** pushes everything after the box powers up or someone turns its knobs, **defaults** puts every cell to a plain setting. The menus (machine, LFO mult, destination, wave) go out as the menu's index in the box's order, and the mute's polarity is the usual Elektron one; the manual gives no values, so these are to verify by ear. The box has no CC for its RETRIG key, so **retrig** is done from here: hold a track's button (latched for the mouse; a MIDI note or CC holds it while down) and the track's note (the map in the Controls tab, the root when off) goes out again at the **rate** (a fraction of the bar at the live tempo, the box's own list from 1/1 to 1/80), the **velocity** fading as the **fade** says (-128 out to nothing, 127 in from nothing) over the **length** (in sixteenth steps, inf flat), until let go. Every cell is a knob or a switch for the MIDI map (the Controls tab, folded groups per track, a **focused track** set with six focus buttons, the delay and reverb, the retrig's settings; the default map puts them on the channel after the last in use), a destination for the LFOs and the macros (the per-track cells, not the focused set), and a scene group of its own, **M:C**, so a scene recalls a kit. With the machine on **sampler** (Model-TG, section 9 of `MODEL_CYCLES_MIDI.md`) the track's color, shape, sweep and contour cells are the sampler's four knobs and carry their names as a prefix, after the **mode** row under the retrig buttons (one shot, loop, slice, granular, stretch, pluck, wave: set it to what the box shows, it names the cells and is not sent, the box alone picks the mode); the pitch cell is greyed and never sent to a sampler track, where that CC would pin the pitch, and in slice mode the note picks the slice (52 is slice 1, the root 60 slice 9). Everything is remembered; the values are not sent at launch, press send all once the box is on.

**MIDI learn**: click the MIDI cell of a row, then press the switch, hit the pad or move the pedal that should do it; the next message becomes the row's binding, the map is saved, and if that control was bound to another action it moves. Click the cell again to cancel, `Delete` or the *clear binding* button unbinds the selected row, *defaults* puts the stock map back. The same learn without going to the tab: **Ctrl-click any knob, switch, menu or slider** anywhere in the interface (the control keeps its value), then move or press the controller; a second Ctrl-click cancels. This one *adds*: the controller keeps whatever rows it drove already, so one knob can turn two rack cells at once, or a pedal can switch a filter in and start a repeat; the tab's cell learn still takes the controller away from its other rows. A row driven by a shared controller shows `(+1)` after its binding, and its tooltip names the others. **Alt-click a control** unbinds its row alone. Rows that are not one control (the shader keys, record, the perform buttons) learn and unbind from the tab. A binding is a note, a control change or a program change (which is what an FCB1010 sends out of the box) with its channel, shown as `note 60 ch1`, `cc 11 ch1` or `pc 5 ch1`; the port is not part of it, so two controllers tell themselves apart by the channel and a binding survives a change of USB socket.

Beyond the keyed actions, the table has MIDI-only rows, greyed in the key column: buttons for *randomize* effects, *grade neutral*, the next shader blend mode, the next section kind and the next picture mode; in the group *video fx: the pool*, one per video effect and one per shader, in or out of the show (the Video FX tab's ticks); and **knobs**, one row per continuous control: A/B, the main volume, the audio sync delay, the shader layer opacity, a *shader pick* knob (off at the bottom of its travel, then each shader in list order), the nine source grade knobs (exposure, black, gamma, contrast, saturation, warmth, tint, sharpen, react), the strength of every video effect, and the audio racks: ten effects and a volume for each of the five channels and each of the seven drum voices, plus the focused set and its twelve focus buttons (see Audio FX). The *drum voices* group has the switches: each voice in or out and its solo, *all voices in*, and *quant_next* for the grid (Perform tab). A knob row takes a CC and spreads its 0 to 127 over the widget's whole range, so a CC on gamma runs 0.4 to 2.5 and one on the sync delay 0 to 2000 ms; the widget moves with it. The two long knob groups start folded.

**Drum pads**: the Controls tab's *drum pads* rows, `hit_kick` to `hit_glitch`, one per drum voice, for any pad controller (and the Erae's Drums page, or its own pads on a native layout so the device's looper can record them): a hit plays that voice's sample from the material the sections are carved from (the kit of the takes or the ticked samples; the hat stutter is a short roll of the closed hat), at the pad's velocity (the velocity layer and the gain), into the voice's own rack on the quantize grid while a section plays and at once otherwise, over the tape whatever the A/B pedal says and whether or not the voice is switched out, and sends the voice's note to the MIDI out at the same instant with that velocity, so a Model:Cycles plays its track from the pad too. With no material yet, the note alone goes out. The Erae tab's *learn the pads* button maps a native pad layout in one go: click it, then tap the pads in order (kick, snare, closed hat, open hat, ride, hat stutter, burst, event); a second click stops early and keeps what was learned. With the MIDI out's *drums only* on, the pads are notes only, like the section's own hits.

**Erae 2 surface** (the Erae tab): the *Erae 2 surface* tick (remembered) turns an Erae 2 into a drawn control surface of eight pages, `gacha_erae.py`. On the device, make a layout in Erae Lab whose eight layouts (the N1..N8 buttons) each hold one API zone over the whole surface, zone index 0 on N1 up to 7 on N8, the finger data rate at its highest; load it and close Erae Lab (Windows lets one program hold the port). Ticked, the app takes the Erae's first MIDI port itself, enables the API, asks every zone its size and draws on each layout the page chosen in the tab (a combo per N button, remembered): **Mix** (the main volume with the output level beside it, the five channel volumes with the stems and the live input under them, Link, MIDI out, the metronome, the eight scenes where a tap loads and a hold saves, the morph switch), **Racks** (twelve focus pads, then the focused rack's eleven effects and its volume as faders), **Picture** (glitch x rgb shift on a spring pad with the pressure on pixel, the shader pick x mix pad, six look faders, the picture switches and video pads), **Section** (next pulsing with the beat, stop, event, burst with its length by height, glitch, break, drop, kind, the seven voices and their solos, the gears, the clock pads), **Time** (the held gestures: repeat with the position across and the division up under the finger, freeze with pitch across, grain size up and the pressure as smear, the tape stop with its length by height, the nudges), **Fragments** (the bar as slices with the playhead running through them, a slice held sounding as grains, motion x pitch with the pressure as repeats, the slice count, direction, play mode, speed, size, rate, shape, attack, release), **Macros** (the eight macro faders, the eight LFOs with their depths, retrigger, all off), **Drums** (a drum pad: the six voices' hits with the pressure as the velocity, the burst with its length by height, the event) and **Loop** (nothing drawn: a layout left to the Erae's own pads, a note each learned in the Controls tab, so the device's looper can record them). Every page carries a status strip at the top: the bar's sixteenths with the beats marked, the loop's bars, the A/B pedal, record, the live input, Link, MIDI out, the section kind, the output level and the volume. Pressing N1..N8 tells the app which page is on screen (the device sends CC 102 + k on channel 16). Fingers arrive as floats, so a fader is finer than a CC, and a held pad keeps writing its knobs from the finger's place and pressure; the LEDs repaint ten times a second, only what changed, from the app's own state, so a knob turned by hand or by another controller shows on the surface too. The rest of a layout (ordinary pads and faders) still sends notes and CCs and lands in the Controls tab's map, on the same port. **MIDI clock to the Erae** and **transport** (the tab's ticks, remembered) put the app's clock and a Start on the Erae's port too, whatever the MIDI out panel says, so the device's looper locks to the show: set the device's clock source to USB device (Settings > MIDI clock) and use firmware 2.0.74 or later. The Start goes out on the live clock's next downbeat, again at D, and with every section's first bar; a section ending sends no Stop unless *stop with the section* is ticked, so a loop runs on over the tape. The tab also mirrors the page on screen with the fingers on it, names the control under the mouse, and documents every page. The pages are the `PAGES` catalogue in `gacha_erae.py`; the protocol is Embodme's Erae API V2. Off, the zones are blanked and the device leaves API mode.

Button actions fire on a note on, a program change, or a CC rising above 63 (and again only after it has gone below, so a footswitch in toggle mode that sends 127 then 0 fires once per press). The `ab` row is continuous: only a CC can drive it, and its 0 to 127 becomes the A/B slider's 0 to 100 %. The **stock map** before anyone learns anything is one note per button from C1 (note 36) up in table order on channel 1, which is what a pad or a small keyboard sends, and CC 11 (expression) for `ab`; the audio racks sit on channel 2 and the drum voices (their switches as notes from 36, their racks' knobs as CCs from 1) on channel 3; channel 1's notes ran out at 127 with the repeat's position and reverse buttons, so those and every button after them (the LFOs, the scenes) continue on channel 4 from note 36; a real controller overwrites it row by row. None of these bring the hidden interface back.

### Drums

| Parameter | Default | Description |
| --- | --- | --- |
| `swing` | random 0-0.06 | Delay of every offbeat 16th as a fraction of a step. `0.33` is a triplet feel, max `0.5`. |
| `humanize` | `0.5` | How much like a person the drums are played, samples and synth alike. Velocities wobble, downbeats lean in, offbeat 16ths sit back, and timing drifts up to a few milliseconds. Every hit exists in three velocity layers: soft hits are lowpassed and shorter, hard hits are saturated. `0` is a machine. |
| `mutation_chance` | `0.3` | Per bar, chance a drum pattern gets mutated. |
| `mutation_amount` | `0.1` | Fraction of steps a mutation touches. |
| `glitch_chance` | `0.15` | Per bar, chance of a hihat stutter burst. |
| `gain_kick` | `0.95` | Kick level. |
| `gain_snare` | `0.8` | Snare level. |
| `gain_hihat` | `0.45` | Closed hihat level. `0` removes closed hats from the sequence. |
| `gain_ohat` | `0.4` | Open hihat level. `0` removes open hats from the sequence. Any drum volume at `0` drops that voice entirely. |
| `gain_ride` | `0.3` | Ride level. |
| `synth_kick`, `synth_snare`, `synth_hihat`, `synth_ohat`, `synth_ride` | `0` | Levels of a synthesized drum machine kit, see below. Each synth voice plays the same pattern as its sample voice, so the two layer; set the sample volumes to 0 for a pure drum machine. |
| `synth_style` | `auto` | Flavour of the synth kit: `house`, `techno`, `dnb`, or `auto` from the drum style (house for four-floor, ukg, minimal, one-drop, boom-bap; techno for halftime, idm, dembow, clave; dnb for dnb, breakbeat, footwork). In the GUI, picking a flavour also sets the five synth volumes to a mix that suits it (house leans on the open hat, techno on the kick, drum and bass on the snare); `auto` leaves the volumes alone. |

Both hats come out of the same source sample, so they read as one instrument. The trick that makes any sample pass for a cymbal: the transient at the onset is mixed with a cloud of tiny grains picked from the whole sample, which turns a flute or a voice into a noisy sizzle in its own colour, then a steep highpass takes the body away. The closed hat is 30 to 70 ms with a snappy decay and a touch of drive. The open hat is 150 to 450 ms with a slow decay, a denser cloud, a resonant band around 7 to 10 kHz for the ring of the cymbal edge, and a small room. Every open hat is cut off by the next closed hat in the bar, or by the next downbeat, with a 5 ms fade.

**Synth kit.** A drum machine in the 909/808 spirit, built from oscillators and noise with no sample involved, jittered a little per song. Kick: a sine with an exponential pitch drop and a highpassed click, soft-clipped. House sits around 48 Hz with a 0.4 s decay, techno drops to 44 Hz with a longer, harder, lowpassed body, drum and bass is tighter and punchier with more click. Snare: two detuned tones that dip in pitch like a 909 plus highpassed noise, snappy in house, darker and shorter in techno, bright and short in drum and bass. Hats: six square waves at the 808's metallic ratios through a bandpass, plus a little noise; the open hat is the same metal ringing longer, and it is choked like the sample one. Ride: inharmonic partials with their own decays, a noise shimmer and a stick click. When a sample voice is at 0 its samples stay free for textures and one-shots.

### Sub bass

A synth sub sits under the kick. Each section's background textures are analysed for their dominant pitch class, and that becomes the section's root note in the sub octave, C1 to B1 (33 to 62 Hz), fifths included, so it always stays a sub and never turns into a bass note. At most one note per bar, on the bar's first kick, and a weighted coin decides whether that bar gets one. Most notes play the root, some the fifth. Each note is a sine oscillator with an ADSR: a one-beat hold, then a long release that rings under the bar. It plays dry on the right and through a slow phaser on the left. The sub stays out of the intro and enters at the drop. Its level is matched to the mix, and the root per section is written to the JSON.

| Parameter | Default | Description |
| --- | --- | --- |
| `sub_level` | `0.6` | Sub level relative to the mix. `0` turns it off. |
| `sub_phaser` | `0.5` | Phaser depth on the left oscillator. `0` gives two dry sines. |
| `sub_pan` | `0.3` | Dry oscillator panned right, phased one panned left by this much. Keep it low for a mono-safe low end. |
| `sub_chance` | `0.6` | Per bar, chance of a sub note on the bar's first kick. |
| `sub_release` | `1.5` | Release in seconds after the one-beat hold. |

### Sections

| Parameter | Default | Description |
| --- | --- | --- |
| `section_bars` | `4,4,8,8,16` | Section lengths in bars to pick from. Repeat a value to make it more likely. |
| `break_chance` | `0.25` | Chance a middle section drops to a break. |
| `fade_in` | `0.3` | Fade-in at the start of the song, in seconds. |
| `fade_out` | `0.03` | Fade-out at the end, in seconds. The default is only a click guard; with an outro style the ending effect's own safety fade handles the silence, and with `none` the outro stays loopable in the Mixer. |

### Drops

A drop is the start of any non-break section. These transitions can lead into it. Each chance applies fully after an intro or a break, and at half strength between two grooves. `0` disables the effect.

| Parameter | Default | Description |
| --- | --- | --- |
| `cymbal_chance` | `0.3` | Reverse cymbal: the ride hit through a huge reverb, played backwards under an opening lowpass, so the wash builds for one or two bars and the hit lands on the downbeat. |
| `repeat_chance` | `0.25` | DJ beat-repeat on the last bar before the drop. The mix is captured and retriggered: accelerating roll, steady 16th stutter, or halving beat by beat, sometimes under a rising highpass. |
| `gap_chance` | `0` | Half a beat to two beats of silence right before the downbeat. Off by default. |

The transitions used are listed per section in the render's JSON.

### Layers and effects

| Parameter | Default | Description |
| --- | --- | --- |
| `layers_min` | `1` | Fewest background textures per groove section. Intros and breaks get 2 when the range allows. |
| `layers_max` | `3` | Most background textures per groove section. |
| `layer_level_min` | `0.18` | Quietest texture gain. |
| `layer_level_max` | `0.4` | Loudest texture gain. |
| `chop_chance` | `0.6` | Per section, chance of a rhythmic chop layer. |
| `chop_gain` | `0.4` | Chop slice level. |
| `fx_min` | `1` | Fewest random effects per texture chain. |
| `fx_max` | `3` | Most random effects per texture chain. The pool has 9. |
| `reverse_chance` | `0.35` | Chance a texture plays backwards. |
| `stretch_chance` | `0.3` | Chance a texture is time-stretched to whole bars. |

Drum hits already seek the loudest transient and chops already sample the whole file. Use it for long recordings, especially ones with a quiet opening. |

Chances are clamped to 0-1 and swapped min/max ranges are sorted, so nothing you type can crash a render.

The GUI writes these as a JSON job file and runs `python3 gacha_engine.py job.json` in a subprocess, so the engine has no command line of its own.

### Outro styles

The ending is a ring-out effect in the spirit of Marmelade's "Ending FX" stage: the body of the song stays dry, the effect blends in over the last bars, then rings out into a tail appended past the last bar, and a safety fade guarantees true silence at the very end. The last section's `end_sec` in the JSON includes the tail, so the Mixer keeps the ending. In the GUI the backdrop video fades to black across the outro.

| Style | Ending |
| --- | --- |
| `hall_wash` | A huge hall swallows the last bars. |
| `dub_echo` | Dotted-eighth dub delay, synced to the tempo, feeding back into a room. |
| `tape_stop` | The reel slows to a halt, pitch dropping with it. |
| `filter_close` | A resonant lowpass closes the door. |
| `shimmer_freeze` | Octave-up shimmer frozen in a cathedral. |
| `bitcrush_collapse` | The mix crumbles into a few bits. |
| `codec_rot` | GSM and low-bitrate MP3 codecs chew the ending up. |
| `glitch_stutter` | A 32nd-note stutter with drive. |
| `overdrive_bloom` | Heavy overdrive blooming into reverb. |
| `smear` | Deep chorus smeared across a long room. |

| Parameter | Default | Description |
| --- | --- | --- |
| `outro_tail` | per style | Seconds of ring-out appended past the last bar, 2.5 to 7 by default depending on the style. |
| `outro_bars` | `2` | The effect blends in over the last N bars. |
| `outro_wet` | `1.0` | Maximum wetness of the ending effect. |
| `outro_amount` | `0.5` | The style's primary knob: decay, feedback or crush depth. |

`four-floor`, `breakbeat`, `boom-bap`, `halftime`, `dnb`, `minimal`, `ukg`, `dembow`, `one-drop`, `footwork`, `clave`, `idm`

## Output

Each render writes two files:

```
output/gacha_ember_20260830_213599_seed42_bpm120.wav   the song (44.1 kHz, 16-bit stereo)
output/gacha_ember_20260830_213599_seed42_bpm120.json  seed, bpm, style, every knob, samples used, section map
```

The word after `gacha_` is drawn from the seed, so reproducing a run gives it the same name.

The JSON section map is what powers the Mixer tab. Finals stitched in the Mixer are saved as `output/final_*.wav`.
